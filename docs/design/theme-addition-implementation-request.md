# 実装依頼: デザインテーマを2つ追加する（ミニマル / ポップ）

作成: 2026-09-13（JST）。依頼者: Techmech keys。実施: 外部エージェント（ChatGPT Work モード）。
作業ブランチ: `design/themes-minimal-and-pop`（このファイルが載っているブランチ）。

役割を終えたら、冒頭に完了印（日付・対応 PR・実機確認の残り）を書いて
[`../archive/`](../archive/README.md) へ `git mv` する。

## 1. 何を作るか

TIL（Techmech keys INPUT LAB）に**デザインテーマを2つ追加**する。既存は
「スタンダード（ダーク HUD）」と「レトロ液晶」の2つ。

| id | 表示名 | 方向性 |
|---|---|---|
| `minimal` | ミニマル | Dieter Rams の "Less but better" に倣った、機能主義の静かな明色デザイン |
| `pop` | ポップ | 高彩度・多色・幾何の遊び。既存3つのどれとも被らない方向 |

**テーマ追加だけで完結させる。** 画面構成・入力処理・Vial 連携・キオスク挙動は変更しない。

## 2. なぜこの2方向か（被らせないための地図）

| テーマ | 明度 | 彩度 | 形 | 質感 |
|---|---|---|---|---|
| スタンダード（既存） | 暗 | ネオン（シアン/赤） | 角丸・中 | ぼかし＋グロー |
| レトロ液晶（既存） | 明（紙） | 無彩色 | 角ゼロ | フラット・等幅 |
| **ミニマル（新規）** | 明（中性グレー） | 低彩度＋機能色を1〜2色だけ | 小さい角丸 | 影・ぼかしを最小に |
| **ポップ（新規）** | 中〜明（色面） | 高彩度・多色 | 太い輪郭・大きい角丸 | ベタ塗り＋幾何パターン |

4つ目に「ポップ」を選んだ理由は、残り3つが**暗い / 無彩色 / 静か**に寄っていて、
**明るくて賑やかな方向**だけが空いているため。検討して外した案:

- ブループリント（濃紺＋白線）: 暗い点でスタンダードと重なる
- 和・墨（和紙＋墨）: 紙・無彩色でレトロ液晶と重なる
- ダークミニマル: スタンダードとミニマルの中間になり、どちらとも見分けがつかない

## 3. テーマの設計指示

### 3.1 ミニマル（`minimal`）

Braun 期の工業デザインの考え方を画面に移す。**装飾を足すのではなく、減らして機能を際立たせる。**

- **背景**: 中性グレーの明色（例 `#f0efed` 前後）。純白にしない。パネルはわずかに明るい面で、
  境界は影ではなく**細い線**で示す。
- **文字**: ほぼ黒（`#1a1a1a` 前後）と中グレーの2段階だけ。3段階以上に増やさない。
  サンセリフのシステムフォント（`-apple-system, "Segoe UI", "Noto Sans JP", sans-serif` 等）。
- **色**: 機能色は**1〜2色だけ**（例: 操作中＝オレンジ系 `#e8620c` 前後、確定・正常＝グリーン系）。
  「色は意味があるときだけ使う」。TrackPoint の赤は製品の識別色なので残してよいが、彩度は落とす。
- **形**: 角丸は 2〜4px。ぼかし（`--blur-*`）は 0。影は使わないか、1段だけの極薄。
- **エフェクト**: カーソル軌跡・波紋・シェブロンは残すが、**グローを消して線を細く**する。
  速度による色相変化はやめ、単色＋濃度で表現する（`--fx-trail-fixed-rgb` を使う）。
- **キーキャップ**: 白に近い面＋細い線。押下は色ではなく**濃度の反転**で示す。
- 迷ったら「この要素は無くても機能するか？」で判断し、無くても機能するなら薄くする。

### 3.2 ポップ（`pop`）

展示で目を引く、賑やかで楽しい方向。**ただし可読性は落とさない。**

- **背景**: 明るい色面（例 クリーム `#fdf6e3` やソフトなミント）。白背景にしない。
- **色**: 4〜6色の高彩度パレット（例: 濃いターコイズ、マゼンタ、イエロー、コバルト）。
  クリック3色・スクロール・コンパスをそれぞれ別の色に割り当てて、賑やかさを機能に使う。
- **形**: 太い輪郭線（2〜3px の黒に近い線）、大きめの角丸（12〜18px）。
  キーキャップは輪郭が強く、押下でベタ塗りに変わる。
- **エフェクト**: 波紋やシェブロンは太く・はっきり。グラデーションよりベタ塗り。
  軌跡は速度で色相を大きく回す（`--fx-trail-hue-start/end` を広く取る）。
- **文字**: 太めのサンセリフ。本文は必ず**背景とのコントラスト比 4.5:1 以上**。
  高彩度の面の上に低コントラストの文字を置かない。
- **やりすぎの線引き**: 背景に動くパターンを足さない（描画コストと展示の目の疲れ）。
  模様を使うならキーボード周辺の静的な装飾だけに留める。

## 4. 実装の型（触るのは4か所だけ）

既存の `ui/themes/lcd.css` が**形の見本**。同じ作り方に揃える。

1. **`ui/themes/<id>.css` を新規作成**
   - 1行目・2行目に SPDX ヘッダ（`/* SPDX-FileCopyrightText: 2025-2026 Techmech keys */` と
     `/* SPDX-License-Identifier: Apache-2.0 */`）。
   - すべての上書きを `html[data-theme="<id>"] { ... }` の中に閉じ込める。
     **他テーマに影響する記述を書かない。**
2. **`ui/themes.js` の `THEMES` 配列に `{ id, name }` を追加**（表示名は日本語）。
3. **`ui/index.html` の `<link rel="stylesheet" href="themes/lcd.css">` の隣に `<link>` を追加。**
4. **`tools/visual-check.js` の `const THEMES = ["default", "lcd"];` に id を追加。**

`ui/style.css` と `ui/stage.css` は**変更しない**。テーマで変えられない色が見つかったら、
自分で構造を書き換えず、**PR 本文に「ここが変数化されていない」と報告する**。

## 5. CSS 変数の契約

`ui/style.css` の `:root` に **67 個**の変数がある。`lcd.css` はその全部を上書きしている。
新テーマも同じ粒度で指定する（既定値を活かしたい変数は書かなくてよいが、
暗色前提の値が残ると明色テーマで破綻するので、色は原則すべて指定する）。

グループ:

| グループ | 変数 | 注意 |
|---|---|---|
| 面と線 | `--bg` `--panel` `--panel-solid` `--line` | `--panel` は半透明可。ぼかしと合わせて調整する |
| 文字 | `--txt` `--dim` `--txt-faint` `--txt-cursor` `--txt-on-accent` `--txt-vial-inherit` `--txt-vial-inherit-sub` | |
| 製品色 | `--red` `--red-deep` `--red-soft` `--red-bright` `--red-cap` `--red-cap-deep` `--red-key-border` `--red-cap-shadow` | TrackPoint とアクセント |
| 補助色 | `--cyan` `--amber` `--green` | 計測値・状態表示に使う |
| ぼかし・角 | `--blur-panel` `--blur-attract` `--blur-osd` `--blur-menu` `--radius-panel` `--radius-key` `--radius-control` | 0 も可 |
| 打鍵 OSD | `--osd-color` `--osd-glow` `--osd-font` `--osd-plate-*` | LCD では判読のため色を変数化した先例あり |
| キーキャップ | `--keycap-bg` `--keycap-border` `--keycap-border-top` `--keycap-shadow` `--keycap-txt` `--keycap-layer-*` | |
| ミッション | `--mission-done-border` `--mission-done-bg` `--mission-flash-rgb` | |
| ガイドツアー | `--tour-scrim-bg` `--tour-spot-bg` `--tour-spot-ring` `--tour-spot-ring-strong` `--tour-spot-shadow` `--tour-spot-shadow-strong` | |
| フォント | `--sans` `--mono` | **Web フォントを読み込まない**（オフライン動作が要件） |
| Canvas 用 | `--fx-*` | 下記のとおり **JS が読む**ので書式厳守 |

`--fx-*` は `ui/app.js` の `refreshFxPalette()` が `getComputedStyle` で読む。書式を守ること。

- `--fx-btn-l` `--fx-btn-m` `--fx-btn-r` `--fx-compass-needle` `--fx-compass-hub`: **CSS 色**（`#rrggbb`）
- `--fx-scroll-rgb` `--fx-halo-rgb` `--fx-compass-rgb` `--fx-compass-needle-start-rgb`:
  **`R, G, B` の数値3つ**（例 `13, 13, 13`）。`rgba()` に埋め込まれるので `#` を書かない
- `--fx-trail-hue-start` `--fx-trail-hue-end`: **数値**（HSL の色相）
- `--fx-trail-fixed-rgb`: 空なら上の色相グラデーション、`R, G, B` を入れると**単色固定**

`--u` はキーの寸法単位。**触らない。**

## 6. 検証（PR 前に必ず実行し、結果を PR 本文に書く）

```sh
node --test tools/boards.test.js tools/scroll-input.test.js tools/vial-layout.test.js
node tools/visual-check.js        # playwright または CHROMIUM_PATH が必要
```

- `visual-check` は **3 画面サイズ × テーマ数 × 15 状態**を撮影する。テーマが 2→4 になるので
  **90 枚 → 180 枚**になる見込み。実際の枚数を確認し、`docs/development.md` の記載を実測値へ直す。
- 撮影時間が CI で問題になるようなら、**新テーマだけ 1 サイズに絞る案**を PR 本文で提案する
  （勝手に既存テーマの撮影を減らさない）。
- スクリーンショットを目視し、次を確認する。
  - 本文・計測値・キー刻印が読めるか（1024×768 と 2560×1440 の両方）
  - キーボードモデルの押下状態・レイヤー刻印・破線（Fn）が判別できるか
  - アトラクト画面、スタッフメニュー、ガイドツアーのスクリムが破綻していないか
  - カーソル軌跡・波紋・シェブロン・コンパスがテーマ色に追従しているか
- **実機（OLSK60 / 展示 PC の WebView2）での確認はこの作業の範囲外**。
  「動作確認済み」と書かず、未確認は `要確認` と明記する。

## 8. 作法

- Git 運用は [`../../.claude/rules/github-workflow.md`](../../.claude/rules/github-workflow.md) に従う。
- コミットは**テーマ1つにつき1コミット**（`minimal` と `pop` を分ける）。
  ドキュメント更新は別コミットでよい。
- PR は**依頼されたときだけ**作る。作るときは 概要 / 変更内容 / 検証 の構成で、
  検証は実行したコマンドと結果を正直に書く。
- リポジトリは Apache-2.0。新規ファイルには SPDX ヘッダを付ける。
- `ui/` は**外部依存なし・オフライン動作**を維持する（CDN・npm・Web フォントを足さない）。

## 9. やってはいけないこと

- `ui/style.css` `ui/stage.css` の構造変更、既存2テーマの見た目の変更
- 画面構成・入力処理・Vial 連携・キオスク挙動の変更
- Web フォントや画像アセットの追加（テーマは CSS 変数だけで表現する）
- 背景アニメーションなど、常時描画が増える演出の追加
- 実機で確かめていないことを「確認済み」と書くこと
