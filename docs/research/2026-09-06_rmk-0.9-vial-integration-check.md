## 1. 結論

1. **Vial 接続経路（Raw HID）は RMK 0.9 系でもプロトコル面の変更なしで通る。**
   TIL が使う 9 コマンドすべてを fork の実ソースで照合し、応答形式・番号体系・ロックの粒度が
   vial-qmk と一致することを確認した（§2）。マトリクステスターのバイト順は 2026-09-02 に
   実機（Vial-RMK）で確認済み（knowledge-base の Entropy 起票記録）。
2. **ただし TIL 側の OLSK60 プロファイルが QMK 版のまま**で、RMK 版に対して 3 点が古い
   （rmk-config `WATCHLIST.md` T-10 と同じ）: Vial UID、matrix 列数（14→13）、
   customKeycodes（名前も個数も違う）。UID は USB VID/PID のフォールバックで救われるので
   表示は切り替わるが、**customKeycodes の不一致でガイドツアーの対象キーが解決できず、
   RMK 版では L2 の設定キーが「USER00」表示になる**（§3）。
3. **詳細スクロール（hi-res / Resolution Multiplier）は「表現できるが、現状は表現していない」。**
   ブラウザの `wheel` イベントはサブノッチ単位で届くので検出は可能。現状はイベント数を
   そのまま数えるため、hi-res 時はライブフィードの ×N が 12 倍に膨れ、標準スクロールとの
   違いが「ノッチが細かい」ではなく「回数が多い」に見える（§4）。
4. **ロータリーエンコーダは現状まったく表現していない。** 配列にエンコーダが無く、回転は
   L0 で `AudioVolumeUp/Down`、L1 で `PageUp/Down` のキー入力として届くだけ（打鍵数に混ざる）。
   L2 の `OCT_UP/DN`（User10/11）は HID 出力が無く、マトリクステスターの対象でもないため
   検出不能。Vial の `GetEncoder`（`0xFE 0x03`）でエンコーダ割当を読み、割当先のキーコードから
   回転を逆引きすれば **L0/L1 の回転と押し込みは表現できる**（§5）。
5. FW 側で 1 件、設計と実装の食い違いを見つけた: **マウスキーのホイール（L3 の `Wh↑↓←→`）が
   Resolution Multiplier を通らない**。hi-res を選んだホストでは 1 tick が 1/12 ノッチになる
   （設計書は「全 producer を L5 に集約し 1 detent を保つ」と規定）。TIL で L3 ホイールキーを
   試すとその差が見える。詳細と扱いは §6（rmk-config `WATCHLIST.md` へ登録）。

## 4. 詳細スクロール（hi-res）の表現可否

### 4.1 FW → OS の事実（fork 実ソース）

- 複合インターフェースのマウスレポート（report id `0x02`）は `wheel: i8` / `pan: i8` を持ち、
  Wheel と AC Pan それぞれの LOGICAL collection に **Resolution Multiplier feature**
  （usage 0x48、report id `0x05`、logical 0..1 / physical 1..**12**）を宣言する（`rmk/src/hid.rs` L176-232）。
- ホストが `SET_FEATURE` で logical 1 を書くと `rmk::usb::resolution_multipliers()` が
  `(12, 12)` を返し、TrackPoint スクロール（`tp_device.rs` `emit_report`）は 1 ノッチを 12 count に
  分けて送る。書かれなければ 1 = 1 ノッチ（detent）。USB 切断・リセットで 1 に戻る。
- Windows（8.1 以降）と Linux（5.0 以降）は feature を読んで hi-res を選ぶ。macOS は保留
  （rmk-config `tp_hires_tenkey_delivery_plan.md`「現在地」）。展示機は Windows なので hi-res 前提。
- **BLE には feature が無い**（USB のみ）。Platyx 無線時は detent 固定になる。

### 4.2 OS → TIL（Chromium / WebView2 の `wheel` イベント）

Windows は hi-res 時、1 count ごとに `WHEEL_DELTA/12 = 10` の `WM_MOUSEWHEEL` を上げる。
Chromium はこれを **ノッチの分数**（`wheel_ticks = 10/120`）として扱い、`wheel` イベントに
次の形で出す（Chromium の実装から。WebView2 実機で `要確認`）:

| プロパティ | 標準スクロール（1 ノッチ） | hi-res（1 count = 1/12 ノッチ） |
|---|---|---|
| `deltaMode` | 0（pixel） | 0 |
| `deltaY` | ±100 前後（OS のスクロール行数設定に依存） | ±8.3 前後（= 1/12） |
| `wheelDeltaY`（非標準・Chromium） | ±120 | ±10 |
| イベント数 / ノッチ | 1 | 12（TrackPoint の押し込み量次第で 1 パケットに複数 count） |

したがって **`|wheelDeltaY| % 120 !== 0`（または `|deltaY|` がノッチ相当より明らかに小さい）
なら hi-res が交渉されている**と判定できる。精密タッチパッドも同じ形で届くので、
「hi-res 判定」は「サブノッチ入力を受け取っている」の意味で表示する。

### 4.3 TIL の現状（`ui/app.js` `wheel` ハンドラ）

- 合計スクロール量 = Σ(|deltaY| + |deltaX|)（px 換算）。hi-res でも 1 ノッチあたりの合計は同じなので**この数字は壊れない**。
- 方向表示・シェブロン（1 イベント 3 本）・ライブフィード（同種連続は ×N 集約）は**イベント単位**。
  hi-res では 1 ノッチで 12 イベント → フィードの ×N が 12 倍、シェブロンが 36 本/ノッチ（上限 60 で頭打ち）。
  「細かい」ではなく「多い」に見える。
- 横スクロール（AC Pan = TrackPoint の横スクロール・L3 `Wh←→`）は合計量に足すだけで、方向表示が無い。

### 4.4 表現案（実装は別 PR）

1. **解像度インジケータ**: INPUT MONITOR のスクロール欄に「標準 / 高解像度（1/12）」を表示。
   判定はサブノッチ入力を初めて受けたら「高解像度」、以降ノッチ整数の入力だけが一定時間続いたら「標準」へ戻す。
2. **ノッチ換算カウンタ**: Σ|wheelDeltaY|/120 を「ノッチ換算」として併記（px 合計は残す）。
   hi-res でも標準でも同じ 1 ノッチ = 1。
3. **フィードの集約単位をノッチにする**: サブノッチ入力は 1 ノッチ分たまるまで 1 行にまとめ、
   「スクロール ↓ ×3（高解像度）」のように出す。
4. **シェブロンの本数をイベント数でなく量に比例させる**: 1 イベントあたり `3 × |wheelDeltaY|/120` 本
   （最低 1 本）。hi-res では連続した細かいシェブロンが流れ、滑らかさがそのまま見える。
5. **横スクロールの方向表示**（◀ ▶）を追加。TrackPoint スクロールと L3 `Wh←→` の両方で使う。
6. `deltaMode` が 1（line）/2（page）の環境（Firefox 等）は px 換算せずノッチ換算だけ表示する。

実機で確認すること（`要確認`）: Surface Pro 7 + WebView2 で表 4.2 の値が出るか／
TrackPoint を軽く押した最小入力で 1 count が 1 イベントとして届くか／
Windows の「一度にスクロールする行数」を変えたとき `deltaY` だけが変わり `wheelDeltaY` は変わらないか。

## 5. ロータリーエンコーダの表現可否

### 5.1 FW の事実

- `keyboard.toml` `[[input_device.encoder]]`: GP15/GP14、`phase = "resolution"`, `resolution = 2`
  （1 ノッチ = 1 アクション。実機校正済み）。回転は `KeyboardEvent::rotary_encoder(id, direction, pressed)`
  として **押下 → 離し の 2 イベント**で流れ、レイヤーごとの encoder map でキーに変換される。
- 割当（`keyboard.toml` `encoders`）:

  | レイヤー | 時計回り | 反時計回り | ホストに届く形 |
  |---|---|---|---|
  | L0 base | `AudioVolUp` | `AudioVolDown` | Consumer report → Windows が `VK_VOLUME_UP/DOWN` に変換 → `KeyboardEvent.code = "AudioVolumeUp"/"AudioVolumeDown"`（`要確認`: WebView2 で keydown が発火するか） |
  | L1 fn | `PageUp` | `PageDown` | `code = "PageUp"/"PageDown"` |
  | L2 control | `User10`（OCT_UP） | `User11`（OCT_DN） | **HID 出力なし**（FW 内部の音階設定） |
  | L3 mouse | `_` | `_` | 透過 → L0 の音量 |

- **押し込み**（GP13）は matrix に無い直接入力で、`encoder_switch.rs` が合成位置 **`(5,12)`** に注入する。
  `keyboard.toml` の `(5,12)` は全レイヤー `Down`（＝ `ArrowDown`）。マトリクステスターの
  応答にも `(5,12)` が立つ（`read_matrix_state` は注入後の状態を見るため。`要確認`）。
- Vial 側: `vial.json` はエンコーダを `0,0 e` / `0,1 e` として持ち、layout option 1「RotaryEncoder」で
  `(5,12)` のキーを出す。割当の読み出しは `0xFE 0x03`（§2 #10）。

### 5.2 TIL の現状

- `ui/layouts/olsk60.js` に**エンコーダの描画要素が無い**。`(5,12)` のキーも無い。
- 回転は `keydown` としてしか届かず、`registerKeyDown` が**打鍵数に加算**して OSD に
  `AudioVolumeUp` の生の `code` を出す（`OSD_LABEL` に無い）。配列に無いので光らない。
- 押し込みは `ArrowDown` として届き、**矢印キーの ↓ が光る**（本物の ↓ と区別できない）。

### 5.3 表現案（実装は別 PR）

1. **プロファイルにエンコーダを追加**: `encoder: { x, y, index: 0, switchMatrix: [5, 12] }`
   （位置は KLE / 実機で `要確認`。vial.json の KLE ではボトム行の後ろに置かれている）。
   描画はノブ + 回転方向のインジケータ（↻ / ↺）+ 押し込みで点灯。
2. **回転の検出は Vial の encoder map から逆引き**: 接続時に各レイヤーの `0xFE 0x03` を読み、
   `{ layer → { cw: keycode, ccw: keycode } }` を持つ。`keydown` の `code` が現在レイヤーの
   cw/ccw に対応するキーコード（`AudioVolumeUp` ↔ 0xA9、`PageUp` ↔ 0x4B…）と一致し、かつ
   その物理キーがマトリクス上で押されていなければ「エンコーダ回転」と分類する。
   リマップ耐性はツアーと同じ考え方（キーコード指定を実行時に解決）。
   - Vial 未接続・ロック中は L0 の既定（音量）だけをフォールバックで見る。
   - L2 の `OCT_UP/DN` は HID 出力が無いので**検出できない**（表示上は「このレイヤーの回転は
     画面に出ません」と注記するか、ツアーで L2 の回転を扱わない）。
3. **打鍵数から除外し、INPUT MONITOR に「エンコーダ ↻ ×N」として集約表示**。
   OSD は `Vol+` / `Vol-` / `PgUp` の刻印で出す。
4. **押し込み**: `(5,12)` のマトリクス状態、または `ArrowDown` keydown の時点で `(4,11)` が
   押されていなければエンコーダ押下とみなす。Vial unlock 済みなら前者を優先。
5. **ガイドツアー**: 「ノブを右に 3 回」「押し込んで…」のステップを追加できる
   （検知フックは 3 関数に集約されているので、encoder 分類を 1 フック足す）。

実機で確認すること（`要確認`）: WebView2 で `AudioVolumeUp` の keydown が届くか
（届かない場合は C# 側の低レベルフックで `VK_VOLUME_UP/DOWN` を拾って `type: "key"` で
転送する。キオスクモード限定）／`(5,12)` がマトリクステスターに現れるか／
1 ノッチで keydown が 1 回（`repeat` なし）か。

## 8. EEPROM レイアウト選択と `vial.json` を表示へ反映する設計（2026-09-07 追補）

照合元: RMK `rmk-v0.9.0` (`986017d9`) と Vial GUI `aef8222a` の
`protocol/keyboard_comm.py` / `editor/layout_editor.py`。以下は両実装と同じ byte order・bit packing を採る。

### 8.1 結論

**可能。** RMK 0.9.0 は VIA 標準の `GetKeyboardValue(LayoutOptions)` を実装し、flash から
復元した 32 bit の layout options を返す。TIL はすでにキオスク経由で端末内の `vial.json` を
取得・XZ 展開しているため、次の 3 情報を組み合わせれば Vial GUI と同じ選択済みキー集合を得られる。

1. `vial.json.layouts.keymap`: 全レイアウト候補を含む KLE 配列
2. `vial.json.layouts.labels`: option の名前と選択肢（存在しなければ切替なし）
3. `0x02 0x02` の応答 `[2..6]`: EEPROM/flash から復元された layout options（big-endian `u32`）

これは「EEPROM の任意領域を直接読む」方式ではない。FW が永続化した値を標準 VIA API で読むため、
保存形式や flash アドレスに依存せず、リポジトリ方針の「Vial 標準機能のみ」に適合する。
読み取りなので Vial unlock も不要である（RMK 0.9.0 の `GetKeyboardValue` 側に lock 判定なし）。

### 8.2 layout options の解釈

`layouts.labels` の各項目は、文字列なら 1 bit の真偽値、配列なら先頭が項目名、残りが選択肢で、
必要 bit 数は `ceil(log2(選択肢数))`。Vial GUI と同じく labels を逆順にたどり、値の下位 bit から
各選択を取り出す。KLE の各キーに埋め込まれた `layout_index,layout_option` と選択値が一致するキー、
および qualifier のない共通キーだけを表示する。

エンコーダー有無は `layouts.labels` の表示名（例えば `RotaryEncoder`）そのものでは判定しない。
名称はキーボードごと・言語ごとに変えられるためである。layout options で qualifier を解決した後の
`layouts.keymap` に、KLE の中央ラベルが `e`、位置ラベルが `encoderIndex,direction` の要素が
1 組以上残るかを判定する。残ればその index のエンコーダーを表示し、0 件なら表示しない。

### 8.3 ボードプロファイルと端末データの合成

TIL の表示モデルは `BoardProfile`（製品設計）を土台にし、`DeviceLayout`（接続機から読んだ状態）を
重ねる。`vial.json` だけから画面全体を作ったり、接続のたびに `BOARD` 自体を書き換えたりしない。

| 情報 | 正本 | 合成規則 |
|---|---|---|
| 製品名、外形、表示領域、テーマ | `BoardProfile` | 常に維持 |
| TrackPoint、タッチパッド等の pointing device | `BoardProfile.pointing` | 常に維持。`vial.json` に無くても消さない |
| ガイド、練習文、製品固有キャプション | `BoardProfile` | 常に維持 |
| キー候補の位置・寸法・matrix 座標 | 取得成功時は `vial.json.layouts.keymap` | layout options 適用後の要素を使う。取得失敗時は `BoardProfile.keys` |
| 選択中の物理 layout option | VIA `0x02 0x02` | `vial.json.layouts.labels` と組み合わせて qualifier を解決 |
| 各キーの刻印／機能 | dynamic keymap | 選択済みキーの matrix 座標に対して現在 layer の値を表示 |
| エンコーダー有無・位置・index | 選択済み `vial.json` | 選択後に encoder 要素が残る場合だけ表示 |
| エンコーダーの CW/CCW 割当 | Vial `0xFE 0x03` | 現在 layer/index の値を表示 |
| エンコーダー押し込み | `BoardProfile` の switch metadata + matrix | OLSK60 固有の `(5,12)` 等を profile 側で関連付ける |

この分離により、OLSK60 では TrackPoint の位置・見た目・ミッションを維持したまま、Space 分割、
ロータリーエンコーダー有無、キー刻印だけを実機状態へ追従できる。汎用キーボードでも同じ
`DeviceLayout` を使えるが、pointing device のようにプロトコルから得られない製品情報は推測しない。
接続解除または definition の検証失敗時は overlay だけを破棄し、元の profile を再描画する。

### 8.4 エンコーダー割当の表示

`vial.json` から encoder index と CW/CCW の描画位置を列挙し、各 layer/index に対して Vial 標準
`0xFE 0x03 <layer> <index>` を送る。RMK 0.9.0 の応答は `[0..2] = CCW`、`[2..4] = CW`
（いずれも big-endian `u16`）なので、既存 `VialKeycodes.describe()` を使ってノブ左右の刻印を
現在レイヤーに合わせて更新できる。VIA の `0x14` は RMK 0.9.0 で未対応なので使わない。

表示データの信頼境界は現行 `vial.json` と同じとし、最大 32×32 matrix、16 layers、64 custom
keycodes に加え、**最大 16 encoder、KLE 要素 256、座標／寸法の有限値・上限**を設ける。
異常な definition、未知の qualifier、範囲外 matrix はその要素だけ捨て、静的 profile へ
フォールバックする。WebHID 単体では外部依存なしの制約により XZ 展開できないため、動的な物理配置は
キオスク版限定となる。現在の静的 profile には encoder 定義がないため、実装を追加するまでは
WebHID 単体でノブを表示しない。

### 8.5 「操作を反映」の限界と採用案

割当の**表示**と回転の**確実な検出**は別問題である。Vial の GetEncoder は設定値を読むコマンドで、
回転イベントを通知しない。matrix tester にも encoder 回転は現れない。そのため、FW 変更なしで
TIL が受け取れるのは、encoder 割当が生成した通常の Keyboard/Consumer HID 入力だけである。

採用案は次の段階に分ける。

1. **確実に実装可能**: ノブ、現在 layer の CW/CCW 割当、押し込み matrix `(5,12)` の点灯を表示する。
2. **条件付きで操作反映**: keydown の `code` が現在 layer の CW/CCW 割当と一致し、同じ割当の
   matrix key が押されていない場合に「推定: encoder ↻/↺」を表示する。通常キーと同じ keycode が
   割り当てられている場合は発生源を一意に決められないため、打鍵数から除外せず「推定」と明示する。
3. **検出不能**: `User10/11` のように FW 内部だけで完結して HID report を出さない割当は、Vial
   標準機能だけでは操作を検出できない。設定値と説明は表示できるが、回転アニメーションは出さない。
4. **完全な発生源識別が必要な場合**: encoder 専用の Raw HID event が必要だが、これは FW 独自拡張に
   なり本リポジトリの方針外。従って TIL の必須仕様にはしない。

また、レイアウト選択値や encoder 割当は Vial GUI から接続中に変更され得る。標準プロトコルには
変更通知がないため、TIL は接続時・手動再読込時に再取得する。常時ポーリングは Raw HID の matrix
poll と競合し、設定値への不要な負荷も生むため行わない。

### 8.6 実装単位と受け入れ条件

1. `VialDevice.readLayoutOptions()` と `readEncoders(layers, indices)` を追加し、big-endian の fixture
   で単体試験する。
2. 外部依存なしの KLE subset parser を追加する。通常キー、encoder、layout qualifier、回転／幅／高さを
   fixture で検証し、未対応 KLE 属性は安全に無視する。
3. `BoardProfile` と分離した一時 `DeviceLayout` を作り、definition → layout options → 選択済み
   key/encoder → keymap/encoder map の順で満たす。全検証が終わってから overlay を一度だけ適用し、
   途中失敗時は破棄する。`pointing` 等の profile 固有要素には触れない。
4. ノブ UI は CCW/CW 刻印、現在 layer、押し込み状態、「推定」操作を区別する。UI 変更後は
   `node tools/visual-check.js` の全 viewport を確認する。
5. OLSK60 実機では RotaryEncoder option の ON/OFF、全 layer の刻印、Vial でのリマップ直後の
   手動再読込、CW/CCW、押し込み、L2 の非検出表示を確認する。

### 9.2 実装前に解消すべき不整合

1. **描画データ参照先**: `BOARD` は選択された製品 profile のままにする。`activeKeys()` のような
   selector を設け、検証済み `DeviceLayout.keys` があればそれを、なければ `BOARD.keys` を返す。
   `buildKeyboard()`、キー数表示、文字対応表、matrix element map は同じ selector を使う。
2. **座標系**: KLE bounds を profile の表示領域へ平行移動・scale する規則が必要。生 KLE 座標だけ
   差し替えるとキーの欠けや TrackPoint との重なりが起こり得るため、OLSK60 profile に
   KLE→製品座標 transform を持たせる。
3. **切断復元**: 現在の `vialRestoreStatic()` は刻印だけを戻し DOM を再構築しない。overlay がキーの
   有無を変える実装後は、切断時に keyboard DOM、`keyEls`、`matrixEls`、キー数、文字対応表を
   profile から一括再構築する。
4. **非該当 matrix 座標**: layout options で非選択になった matrix 位置は DOM に作らない。
   matrix tester がその位置を返しても無視し、別の可視キーへ流用しない。
5. **profile 判別**: 複数 UID を登録する目標に対し、現行 `findBoard()` は単一 8-byte UID だけを扱う。
   配列対応を先に実装しないと RMK UID から OLSK60 profile を確実に選べない。
6. **更新の原子性**: definition、layout options、keymap、encoder map の全検証完了前に
   `VS.rows/cols` や DOM を部分更新しない。静的キーと端末由来 matrix 次元の混在を防ぐ。

### 9.3 ハイレゾスクロールの現状判定

現行 wheel handler は `deltaX/deltaY` を受け取り、絶対値合計、上下方向、シェブロン、feed を更新する。
従ってサブノッチ入力がブラウザへ届けば**何らかのスクロールとしては表示される**。しかし次を実装して
いなかったため、この点検時点では標準スクロールとの違いを認識できる状態ではなかった。

- `wheelDeltaX/Y` または正規化量による 1/12 ノッチ判定
- 標準／高解像度インジケータ
- ノッチ換算の蓄積と端数 accumulator
- event 数ではなくスクロール量に比例する feed／シェブロン集約
- `deltaX` の左右方向表示（現状は合計値へ加算するだけ）

現行は 1 event ごとにシェブロンを3本生成して feed の回数を増やすため、1ノッチが12 eventに分かれる
環境では標準入力の約12倍の操作に見える。クラッシュや計数不能ではないが、展示上の意味が誤っている。
§9.5 の受信基盤追加後の判定は **FW経路: ソース上対応、TIL受信・換算表示: 対応、
実機値: 要確認、エフェクト／横方向を含む完全表現: 未対応**。

実装時は vertical/horizontal ごとに signed accumulator を持ち、`wheelDelta* / 120` を優先して
ノッチ換算する。値がない環境では `deltaMode` を含むフォールバックを使う。ただし precision touchpad
もサブノッチ値を出すため、表示はデバイスを断定する「FW Hi-Res」ではなく「高解像度スクロール」とする。

### 9.4 OLSK60 の統合エンコーダー表現

OLSK60 の RotaryEncoder layout option が有効な場合、Vial definition 上では回転用 encoder 要素と
push switch `(5,12)` が別要素でも、TIL では通常の `ArrowDown` キー位置に**単一のノブ**として描画する。
これは全ボード共通の推測ではなく、OLSK60 `BoardProfile` に次の関連付けを持たせる製品固有表現とする。

```js
encoderPresentation: {
  index: 0,
  replaceMatrix: [4, 11],
  pushMatrix: [5, 12],
  fallbackCode: "ArrowDown",
}
```

- layout options 適用後の `vial.json` に encoder index 0 の CW/CCW 要素が1組残る場合だけ統合ノブへ置換する。
- `[4,11]` の通常下カーソルkey DOMと、encoder用の2要素およびpush switch用key DOMを重複描画しない。
- ノブ中央はpushを表し、matrix `(5,12)` のdown/upで押下表示する。中央刻印はpush switchのdynamic
  keymap値を使用するため、`ArrowDown`からリマップされても追従する。
- ノブ左右は `0xFE 0x03` で読んだCCW/CW割当を表示し、推定できる通常HID入力時だけ左／右回転を発光する。
- optionが無効、encoder要素が片方向しかない、indexがprofileと一致しない場合は置換せず、通常の
  下カーソルキーを表示する。push switchだけをノブと誤認しない。

この構成なら、TIL上の一つの操作部品で「中央push・左回転・右回転」を表現しつつ、Vial標準の
独立した設定値を失わない。物理位置の正本はOLSK60 profile、存在判定と割当の正本は接続機とする。

### 9.5 ハイレゾ受信基盤の整備結果

`wheel` eventからChromium非標準の `wheelDeltaX/Y`（なければ `wheelDelta`）を読み、120 unitsを
1ノッチとして絶対量を蓄積する処理を追加した。**1 detent 未満（120 units 未満）のsampleを
一度でも受けた場合**に「高解像度スクロール」と表示する。これにより、受信・判定・ノッチ換算の
入口は実装済みとなった。

判定条件を「120 で割り切れないか」ではなく「1 detent 未満か」にしているのは、割り切れない値が
ハイレゾ機以外からも出るためである。ハイレゾ機の定義は *1 detent を分割して送る* ことなので、
sub-detent かどうかが本来の判別条件になる。120 以上の端数（表示スケールやページズームで
倍率のかかった値、coalesce された値、float 誤差）を高解像度と読むと、展示 PC で普通のマウスが
「高解像度スクロール」と表示されてしまう。

Windows では `wheelDelta` は `WM_MOUSEWHEEL` の生値と同じで、「一度にスクロールする行数」の
システム設定を変えても値は変わらない（MDN `mousewheel` event）。したがって行数設定は本判定に
影響しない。ハイレゾ機は同 message で 120 の分数（例: 10）を送るため sub-detent として検出できる。

ただし今回は操作情報の受信基盤までで、既存のシェブロンとfeedはevent単位のままである。
横方向UI、signed accumulator、ノッチ単位のeffect集約、実機での `wheelDeltaY=10` 確認は残課題である。
`wheelDelta*` がないブラウザではpixel/line deltaから倍率を推測せず「解像度を測定中」を維持する。

#### 検証（2026-09-07・本セッションのコンテナ）

- 判定表を fixture で確認（`readScrollTelemetry` を app.js から取り出して実行）。
  `120`／`240`／`180`（1.5倍された1ノッチ）／`119.99997`（float 誤差）＝標準、
  `10`／`40`（sub-detent）＝高解像度、`wheelDelta` 非対応＝測定中。全 8 件 pass。
  なお旧条件（`% 120 !== 0`）では `180` と `119.99997` が高解像度と誤判定される。
- `node tools/visual-check.js` を Chromium で実行（全 3 viewport × 2 テーマ）。加えて
  `#inputMonitorPanel` を単体撮影し、「ノッチ換算」と解像度バッジ追加後も
  `scrollHeight == clientHeight`（あふれなし）、LCD テーマでもバッジが可読であることを確認。
- CDP の合成 wheel は tick を必ず ±1 にするため、**サブノッチ経路はこの環境では実行できない**。
  ハイレゾ判定・`wheelDeltaY=10` の確認は実機（OLSK60 + 展示 PC）でのみ可能で、未実施。
